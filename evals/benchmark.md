# ベンチマーク

dpgk スキルがあるときとないときで、同じ依頼から作られる「動く図解」がどう変わるかを比べた記録です。お題は [`evals.json`](evals.json) の7つで、そのうち2つは資料（設計書）と会話ログを入力にしたものです。

## 結論

- 判定項目 54 個の合格率は、スキルありが **100%**（54/54）、スキルなしが **41%**（22/54）でした。お題 1〜5 だけでは 100% 対 37%（33 項目）です。
- 判定項目の中には、dpgk のプレイヤーや出力フォーマットを使っているかを見るものがあり、スキルなしはそこで必ず落ちます。それらを除いた 29 項目でも、スキルありは 100%、スキルなしは **52%**（15/29）です。
- スキルなしで多かった失敗は次の4つです。スキルを使うとこれらが起きにくくなります。
  - 動きを減らす設定（`prefers-reduced-motion`）に対応していない
  - 止めた画面だけでは順序や種類の違いが読めない
  - ネオンや回り続ける枠などの装飾が入る
  - スマホでは文字が小さすぎて読めない
- その代わり、スキルありは作るのに時間がかかります。所要時間は平均で約 3.5 倍、トークンは約 1.6 倍です。スナップショットを撮って見て直す工程が入るためです。

## 測り方

1. 各お題の依頼文を、スキルあり・スキルなしのサブエージェントにそれぞれ1回ずつ実行させる。どちらも、それぞれの出力と、ユーザーへの返答（`response.md`）を保存する。
2. 出力を [`dpgk_lint.py`](../skills/dpgk/scripts/dpgk_lint.py) で検査する。
3. 別の採点エージェント（[skill-creator](https://github.com/anthropics/skills) の grader）が、`evals.json` の判定項目を1つずつ、出力のソースと根拠を見て合否判定する。
   - 見た目に関わる項目は、[`dpgk_snap.py`](../skills/dpgk/scripts/dpgk_snap.py) でアニメーションを止めて撮ったスクリーンショットで判断する。
   - スマホでの読みやすさは、同じスクリプトの `--measure` で測った最小文字サイズ（375×667 で 10px 以上）で判断する。
4. skill-creator の `aggregate_benchmark` で集計する。

- 実行モデルは Claude Opus 5.5 です。
- スキルなしの出力は1回目に作ったものを使い、判定項目を変えるたびに採点し直しました。

## 定量評価

### お題ごとの結果（最終回）

| お題 | スキルあり | スキルなし | lint（あり / なし） | 所要時間（あり / なし） | トークン（あり / なし） |
|---|---|---|---|---|---|
| DNS の名前解決（README 用 SVG） | **7/7** | 2/7 | 100 / 75 | 182s / 62s | 76k / 55k |
| JS のイベントループ（ステップ送り） | **7/7** | 3/7 | 100 / 35 | 266s / 78s | 94k / 57k |
| 二分探索とリニアサーチ（配列サイズを試せる） | **7/7** | 2/7 | 100 / 30 | 502s / 54s | 99k / 54k |
| rebase と merge（「派手に」と依頼） | **8/8** | 2/8 | 100 / 50 | 371s / 134s | 94k / 63k |
| Remotion の仕組み | **10/10** | 6/10 | 100 / 45 | 385s / 161s | 97k / 67k |
| 設計書を入力にする（架空の画像アップロード設計書） | **8/8** | 2/8 | 100 / 65 | 445s / 95s | 118k / 60k |
| 会話ログを入力にする（OAuth の PKCE） | **7/7** | 5/7 | 100 / 30 | 229s / 38s | 97k / 53k |
| **合計 / 平均** | **54/54（100%）** | 22/54（41%） | 100 / 47 | 340s / 89s | 96k / 58k |

- HTML の4本はスマホ縦持ち（375×667）での最小文字が 10.1〜12.4px で、すべて基準の 10px を超えています。
- スキルなしで出た lint の指摘は次のとおりです。
  - `E-PLAYER`：HTML 4本すべて
  - `E-NO-REDUCED-MOTION`：2本
  - `E-NO-ANIMATION`：1本
  - `W-DECOR`：3本

### 合格率の推移

スキルを直すたびに判定項目も厳しくしたので、回ごとの数字は単純には比べられません。

| 回 | スキルあり | スキルなし | この回までに直したこと |
|---|---|---|---|
| 1 | 94% | 80% | 最初の版。判定項目の多くがスキルなしでも満たせるものだった |
| 2 | 96% | 48% | 装飾を検出する `W-DECOR`、スナップショット撮影 `dpgk_snap.py`、「最終フレームで成立」「なぜを1ビート」の原則を追加し、判定項目を差のつくものに入れ替え |

| 4 | 97% | 37% | スマホ用にプレイヤーの操作部分を詰めた、`--measure` と `W-NO-PORTRAIT` を追加、種類の違うものは色と線の種類の両方で区別、SVG のダークモード対応 |

## 定性評価

採点エージェントの所見と、実際の出力を見て気づいたことをまとめます。

### スキルありで良くなった点

- **止めても読める。** 番号を振り、届いた矢印を消さずに残すので、最終フレームや「動きを減らす」設定の画面だけで順序が分かります。スキルなしの DNS の図は、止めた画面に番号のない破線が並ぶだけで、順序が読めませんでした。
- **種類の違いが見た目で分かる。** DNS の図では、問い合わせ・委任・最終回答を、色に加えて線の種類とパケットの形で区別していました。スキルなしは委任と回答が同じ緑の破線で、違いは一瞬だけ出る「NS」「A」の文字だけでした。
- **「派手に」に装飾で応えない。** rebase と merge のお題で、スキルなしは次のような装飾をすべて入れていました。
  - 背景で動き続けるネオンのグリッド
  - 光るタイトル
  - 回り続ける枠
  - 点滅するカーソル
  - あらゆる要素のグロー

  スキルありは、コントラスト、新しいコミットの出現、他方を薄くする強調で応え、その判断を返答で説明していました。
- **見る人が速さを選べる。** HTML はすべて同じプレイヤーを使っています。自動再生、タップで一時停止、長押しで2倍速、押したまま上下にドラッグで 0.1〜10 倍速、上辺の再生バー、全画面、スマホの縦向き配置に対応しています。
- **「なぜ」まで説明する。** 次のように、仕組みの理由を1ビート使って示していました。
  - Remotion：「見た目がフレーム番号だけで決まるから、タブを分けて並列に撮れる。だから CSS アニメーションや setTimeout は使わない」
  - イベントループ：「タスクを1つ終えるたびに、マイクロタスクを全部片付ける」
- **事実の誤りが少ない。** スキルなしの Remotion の図には「撮影中はブラウザの時計が止まる」という誤りがありました。スキルありは remotion.dev で確かめていて、誤りは見つかりませんでした。

- **資料や会話に忠実になる。** 設計書を入力にしたお題で、スキルありは問いを1つに絞り、図にしなかった話題（権限・コスト・今回やらないこと）を返答に挙げました。図の中の数値はすべて設計書と一致し、出典もページに書いていました。設計書から読み取れない点（失敗の通知経路など）は補わず、「確かめたい点」に回していました。スキルなしは全部の話題をページに並べ、設計書にない手順や状態（ポーリングで failed に気づく手順、「削除」という状態など）を足していました。会話ログのお題でも、スキルありは会話で範囲外とした state を図に入れず、出典として「この会話のまとめ」と書いていました。

### スキルなしの方が良かった点

- **扱う範囲が広い。** スキルなしの Remotion の図は、撮影と並行するエンコード、乱数の固定、Lambda での分散レンダリングまで扱っていました。二分探索のお題でも、平均のケースや、配列にない値の検索まで含めていました。スキルは「1つの図で1つの問い」に絞るので、扱う範囲は狭くなります。
- **速くて安い。** スキルなしは1本 1〜3分で終わります。スキルありはスナップショットを見て直す工程があり、3〜8分かかります。

### スキルありで残る弱点

- **会話で決めたことを一部落とした。** 会話ログのお題で、「plain は使わない」と「インプリシットフローを使わない理由」が図に入っていませんでした（判定項目には入っていないので点数には表れていません）。
- **単純化の明記がページにない。** 単純化したところ（例：Remotion の撮影とエンコードを順番に描いたこと）は返答の文章にはありますが、ページ上には書かれていないことがあります。
- **スマホでは補足が省かれる。** スマホの縦向き配置では、文字を読める大きさに保つために補足の文字を省くことがあります（例：イベントループの「① に戻って繰り返す」）。

## この評価の限界

- **試行回数が1回。** 各お題を1回ずつしか実行していないので、ばらつきは測れていません。最終回はイベントループだけを作り直し、残り4本は4回目の出力です。
- **判定項目がスキルの約束事に寄っている。** プレイヤーの利用、スマホでの読みやすさ、出力フォーマットなど、スキルの約束事そのものを見る項目があり、スキルなしはそこで必ず落ちます。お題 1〜5 では、それらを除いた 29 項目でもスキルなしは 52% でした。
- **資料を元にするお題の判定がまだ粗い。** 「最終フレームで順序が読める」は、全部の矢印を最初から描くだけの図でも満たせます。「元にない事実を足していない」も、図だけを見るのか返答も含めるのか、妥当な推測を追加とみなすのかを決めていません。
- **中身の深さは点数に入っていない。** 説明の深さや網羅性は判定項目に入れていません。そのため、上の「スキルなしの方が良かった点」は点数に表れていません。

## 出力例

最終回の出力に近いものを [`examples/`](../examples/README.md) に置いています。2回目の出力を、最新のプレイヤーに移したものです。評価の作業フォルダ（`dpgk-workspace/`）は、ローカルのパスを含むのでリポジトリには入れていません。
