# 画像アップロード処理の設計（Hozuki 写真共有サービス）

> 評価用に作った架空のサービスの設計書です。

## 背景

Hozuki はユーザーが写真をアップロードして家族と共有するサービスである。これまでは API サーバーが画像を受け取ってストレージに保存していたが、大きな画像で API サーバーのメモリが不足する障害が月に 2 回ほど起きていた。そこで、クライアントがストレージへ直接アップロードする方式に切り替える。

## アップロードの流れ

1. アプリが API サーバーに「アップロードしたい」と伝える（`POST /uploads`）。このとき、ファイルサイズと MIME タイプを送る。
2. API サーバーはサイズが 20MB 以下で、MIME タイプが `image/jpeg` か `image/png` のときだけ受け付ける。受け付けたら、`uploads` テーブルに状態 `pending` の行を作り、オブジェクトストレージへの署名付き URL を発行して返す。署名付き URL の有効期限は 10 分。
3. アプリは署名付き URL に画像を直接 PUT する。API サーバーは画像の中身を受け取らない。
4. ストレージへの保存が終わると、ストレージがイベントを発行し、サムネイル作成ワーカーが起動する。
5. ワーカーは 3 種類のサムネイル（200px、800px、1600px）を作り、同じストレージの `thumbs/` に保存する。
6. ワーカーは `uploads` の状態を `ready` に更新する。
7. アプリは 2 秒おきに `GET /uploads/{id}` で状態を確認し、`ready` になったら写真を表示する。

## 失敗したとき

- 署名付き URL の期限が切れた場合、アプリは手順 1 からやり直す。`pending` のまま 24 時間たった行は、夜間のバッチが削除する。
- サムネイル作成に失敗した場合、ワーカーは 30 秒、2 分、10 分の間隔で最大 3 回やり直す。3 回とも失敗したら状態を `failed` にし、運用チームの Slack チャンネルに通知する。
- アプリは状態が `failed` になったら「アップロードに失敗しました」と表示し、再アップロードのボタンを出す。

## 権限

- 署名付き URL は、そのアップロード 1 件のオブジェクトキーにだけ書き込める。
- 共有アルバムのメンバーは、`ready` の写真だけを閲覧できる。`pending` と `failed` の写真は、アップロードした本人にしか見えない。

## コスト

- ストレージ転送量は従来とほぼ同じ見込み。API サーバーの台数は 6 台から 4 台に減らせる見込み。
- サムネイル作成ワーカーの実行時間は、1 枚あたり平均 1.2 秒。

## 今回やらないこと

- 動画のアップロード
- 画像の自動回転（EXIF の向き情報の反映）は次のリリースで対応する
